# Procedure: Communications (docs/comms/)

The convention for stakeholder-facing material and the style law for writing
it. Convention ONLY, by design: there is no comms command and no comms agent,
and none should be added -- an outgoing artifact is authored by whatever
session was asked for it, under this law. This file slots at the
command/procedure-law rung of `harness/procedures/precedence.md`.

## The directory convention

Stakeholder communications live in `docs/comms/` at the project root, split
into two sides:

```
docs/comms/
  incoming/   -- dated citable evidence: material stakeholders sent
  outgoing/   -- the durable record of what was said to whom
```

- **incoming/** holds material stakeholders SENT -- meeting notes, emails,
  circulated documents. It exists so later sessions CITE the artifact instead
  of describing it from memory. Store the artifact verbatim as received;
  never edit, summarise-in-place or reformat it -- a summary is a second
  author for evidence that must have exactly one.
- **outgoing/** holds what was actually said to whom: the sent version of an
  email, report, briefing or deck. It is the record a later session consults
  to know what a stakeholder has already been told. File the version that was
  sent (or is being handed over for sending), not working drafts.

**Naming: `DDMMYY_<topic>` on both sides** (e.g. `140826_dashboard_briefing.md`)
-- the date the artifact was received (incoming) or sent (outgoing).

The two subdirectories are generated by `/bootstrap_to_custom_commands`
scaffolding; in a project bootstrapped before they existed, create them on
first use.

## Style law (outgoing)

Short by design: this is law, not a writing guide.

1. **Calibrate to the reader's ROLE.** The same finding is written
   differently per reader role: operational detail in the reader's own units
   for an operational audience; decision-plus-cost brevity for an executive
   audience; clause-level precision with no adjectives for a legal audience.
   Those are illustrations, not a list to pick from -- see rule 3.
2. **The audience is NAMED BY THE REQUESTER.** An outgoing artifact is
   authored for the audience named in the request. When no audience is named,
   ASK -- do not guess. No mechanism infers the audience; that absence is a
   design choice, not a gap.
3. **No audience taxonomy ships in the harness.** Audiences are
   project-specific and live in the host project's CLAUDE.md and context
   files; any list shipped here would rot.
4. **Concise and precise.** Every sentence earns its place for THAT reader;
   drop what the reader's role does not need.
5. **Host-project rules COMPOSE.** Host-specific constraints on outgoing
   material (legal conditions, crediting rules, distribution limits) stay in
   the host CLAUDE.md, bind on top of this law, and are never restated in the
   harness corpus.
